# 서버 사양, 가용량, 관리자 장애 알림

자원 → **서버 사양**에서 CPU 모델·소켓·물리/논리 코어, CPU 사용률·1분 부하, 호스트 RAM 전체·가용·사용 추정, 스왑, 실행 환경의 디스크 가용량, GPU·VRAM을 확인한다. RAM 가용량은 Linux `MemAvailable`이며 단순 `MemFree`가 아니다. 전체−가용을 사용 추정으로 표시한다. 컨테이너의 CPU 허용 범위·할당 제한 및 메모리 제한·잔여량은 별도로 표시하며 물리 호스트 가용량과 합산하지 않는다. 파일시스템 가용량은 해당 수집 계정의 `f_bavail` 기준이다. 파일시스템 간 공유 저장공간이 있을 수 있으므로 합계를 제공하지 않는다.

RAM DDR 종류·클럭·DIMM 슬롯, 디스크 물리 모델과 접근 불가능한 호스트 마운트는 현재 수집하지 않는다. 누락값은 미수집/확인 불가이며 0으로 바꾸지 않는다. 보고가 실패하면 사양은 보존하지만 현재 가용량은 숨긴다.

## 현재 연결 범위 (2026-10-21)

| 식별자 | 구분 | 수집 범위 |
| --- | --- | --- |
| `pro_6000_dgu` | 로컬 PRO6000 서버, 수집 환경 `dgu-box` 컨테이너 | CPU/RAM/디스크 직접 읽기 + 기존 GPU 보고 |
| `dami-0` | **클라우드 서버: 사용자 제공 분류**, 제공업체·계약 사양 미확인 | 기존 H200 GPU 보고; CPU/RAM/디스크 연결 없음 |

클라우드 서버에 임의 SSH 접속 정보를 추정하거나 기존 ERP 계정·수집 토큰을 전용하지 않는다. 클라우드 상세 사양은 이후 허가된 접속 경로가 제공되면 연결한다.

## 수집 설정

`LAB_SERVER_TARGETS_FILE`은 운영자 전용 JSON 파일을 가리킨다. 로컬/SSH 방식은 30초마다 Python 표준 라이브러리로 읽기만 수행한다. 동시에 최대 두 호스트, 대상당 8초 제한, 최대 16개 대상이다. SSH는 기존 키·known_hosts를 사용하며 비밀번호 입력이나 호스트 키 자동 승인을 하지 않는다. 스크립트는 stdin으로 전달하므로 원격 서버에 파일을 설치하지 않는다.

```json
[
  {"host":"pro_6000_dgu","transport":"local","expectedHostname":"dgu-box","hosting":"local"},
  {"host":"dami-0","transport":"gpu","hosting":"cloud","note":"클라우드 서버로 별도 관리. CPU·RAM·디스크 미수집."}
]
```

추가 서버의 예: `{"host":"lab-node","transport":"ssh","sshAlias":"existing-ssh-alias","expectedHostname":"actual-hostname"}`. `host`는 기존 GPU 식별자와 같아야 합쳐진다. `expectedHostname` 불일치는 수집 실패로 처리한다. `transport: gpu`는 기존 GPU heartbeat만 사용한다. 목록은 브라우저에서 받은 실행 명령이나 URL로 구성되지 않는다.

## 역할과 알림

설정 또는 자원 → 서버 사양 → **서버 관리자 지정**에서 워크스페이스 관리자가 지정한다. 최초 활성화 때 기존 워크스페이스 관리자들을 수신자로 등록하며 이후 역할은 독립적이다. 일반 구성원을 서버 관리자로 지정해도 사용자/도메인/예약 관리 권한은 승격되지 않는다. 마지막 수신자는 제거할 수 없다.

서버 관리자만 들어갈 수 있는 별도 비공개 채널을 생성한다. 역할 회수 시 채널 접근과 장애 기록 조회가 함께 제거된다. 일반 채널 구성원 추가 API로 이 채널의 역할 제한을 우회할 수 없다. 역할 변경은 관리 기록에 남긴다.

- 마지막 유효한 보고에서 3분이 지나면 보고 중단 사건 하나를 기록하고 지정 관리자들을 멘션한다. 부팅 식별자 변경은 별도 재시작 관측으로 기록한다.
- 보고 중단은 전원 꺼짐 증명이 아니다. 네트워크·수집기·중앙 GPU 서비스 실패도 원인일 수 있다. GPU만 연결된 서버는 그 근거를 명시한다.
- 같은 사건은 재시작 후에도 반복 발송하지 않는다. 복구는 30초 이상 진행된 새 샘플로 확인한다. 같은 과거 샘플 반복은 복구가 아니다.
- 초기 알림 후 AI 분석을 수행하며 실패해도 알림·사건 기록은 유지한다. 분석 완료 후 원인 후보와 수동 점검 순서를 추가한다. 해결 사건 메타데이터는 90일 보관하고 채팅 기록은 기존 정책을 따른다.
- 웹은 멘션/읽지 않음 표시, 데스크톱은 기존 채널 알림 정책을 사용한다. 앱 실행·로그인·OS 알림 허용이 필요하며 완전히 종료한 앱에 푸시하는 서비스는 아니다.

**PRO6000 자체 정지 시 이곳에서 실행되는 감시·채팅도 함께 정지한다.** 이 경우까지 알리려면 다른 장비/클라우드에서 감시하고 독립된 알림 수단을 운영해야 한다. 현재 외부 감시자는 배치하지 않았다. 이 구현은 서버 전원·프로세스·작업을 자동 복구하지 않는다.

## Codex SDK

공식 [Codex SDK](https://learn.chatgpt.com/docs/codex-sdk)의 서버용 `@openai/codex-sdk` 0.163.0을 사용한다. 앱/Electron 번들에는 포함하지 않는다. `LAB_INCIDENT_CODEX_PATH`로 기존 CLI를 재사용한다. 빌드가 끝난 별도 서버 런타임에서 `npm ci --omit=dev --omit=optional`로 설치하면 SDK의 선택적 CLI 바이너리를 중복 설치하지 않는다. 개발 빌드의 TypeScript/Vite는 플랫폼별 optional 패키지가 필요하므로 이 명령을 빌드 전에 사용하지 않는다.

현재 로그인 사용은 운영자가 명시적으로 승인한 인증 파일 경로만 심볼릭 링크로 연결한다. 별도 `incident-ai/codex` 상태 디렉터리와 빈 작업 폴더를 사용하며 사용자 설정, MCP 서버, ERP 토큰을 복사하지 않는다. 기존 인증 파일의 이름·경로가 바뀌면 운영자가 재연결해야 한다. 인증 링크가 다른 파일로 대체된 경우 시작 시 검증 실패로 중단한다.

공식 [설정 레퍼런스](https://learn.chatgpt.com/docs/config-file/config-reference)에 따라 명령 도구·브라우저·앱·훅·다중 에이전트·스킬·웹 검색을 비활성화하고 읽기 전용 샌드박스를 적용한다. 기본 코딩용 지침 대신 짧은 관측값 분석 지침을 사용한다. 전송 데이터는 서버 식별자, 보고 시각, 실패 여부, 마지막 CPU/RAM 수치뿐이다. 채팅 내용·명령줄·로그 원문·계정 비밀은 전송하지 않는다. 결과는 추정으로 표시하며 자동 명령 실행은 없다.

한 번에 1건, 전체 시간당 최대 4건, 호출당 90초 제한이다. 재시작 중 끊긴 분석은 `interrupted`로 남기며 자동 재실행으로 비용을 늘리지 않는다. 활성 계정의 Codex 사용 한도를 소비한다. SDK 오류 원문은 사용자에게 전달하지 않는다.

## 검증

`npm test`의 서버 경계·장애 지속성·역할/채널 권한·수집기·SDK 설정 테스트와 `test/browser/servers.spec.mjs`의 실제 UI 검증을 실행한다. 가짜 장애와 멘션은 격리 DB에서만 생성한다. 실제 서버를 끄거나 운영 채널에 테스트 알림을 보내지 않는다. 실제 SDK 검증은 별도의 합성 카운터로 실행하며 운영 데이터·알림을 변경하지 않는다.
