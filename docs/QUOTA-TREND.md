# CLI 사용량 추이

**연구 자원 → AI 사용량·한도 → CLI 사용량 추이**에서 계정, 최근 24시간·3일·7일,
잔여율·사용률을 선택한다. Codex와 Claude 모두 주간 한도를 기준으로 표시한다.
Codex의 5시간 항목은 다시 도입하지 않는다. 현재 카드의 15분 최신성 판정과 달리
이력은 당시의 기록을 보여주므로 오래된 정상 표본도 보존한다.

## 의미와 공백

잔여율은 ERP가 관측한 주간 한도의 남은 비율이며 사용률은 `100 - 잔여율`이다.
구간별 소비량, 토큰 수, API 비용을 계산하는 그래프가 아니다. 한도 초기화나 보충이
있어도 이를 소비량으로 합산하지 않는다. 오류·없는 수치는 `null`이며 0으로 채우지
않는다. 0%는 유효한 관측값이다.

실패 표본 앞뒤, 관측 간격 30분 초과, 잔여율 상승, 보고 창 변경, 리셋 예정 시각의
1분 초과 변경 또는 예정 시각 통과, ERP의 resetEvent가 있을 때 선을 끊는다.
이는 보수적인 불연속 표시이며 실제 리셋 원인을 확정하는 판정이 아니다.
표에서는 오류를 안전한 한국어 분류로 표시하고 세부 원문·자격증명은 전달하지 않는다.
최신 기록부터 50행씩 볼 수 있으며 계정을 바꾸거나 새로 조회해도 펼친 표는 유지한다.

## API와 소유권

`GET /api/resources/quotas/history?account=dami-codex&days=7`

기존 로그인 세션이 필요하다. `account`는 현재 ERP 계정 목록의 Codex/Claude ID,
`days`는 1(기본값), 3, 7만 허용한다. 서버는 고정된 ERP
`GET /api/ai/usage-history?account=...&period=10080&since=...`를 호출한다.
사용자가 URL·경로·주간 이외의 창을 지정할 수 없다. 임의 계정은 404,
잘못된 기간은 400, 인증되지 않은 호출은 401이다.

응답은 `{data, fetchedAt, source: "erp", demo: false}`다. `data`는 `account`,
`from`, `to`, `startedAt`, `intervalMs`, `limited`, `points`를 포함하며 시각은
밀리초다. 각 표본은 `at`, `remaining`, `used`, `resetsAt`, `issue`, `breakReason`을
포함한다. `breakReason`은 `error`, `gap`, `reset_or_change` 또는 `null`이다.
계정·기간·조회 시작값의 응답 일치, 시간 범위, 중복 시각, 최대 11,000개 표본을
검사한다. ERP 반환 한도 11,000개에 도달하면 `limited: true`로 표시하고 이후
표본이 누락되었을 수 있음을 알린다. 서버가 원본 이력을 삭제·수정하지 않는다.

`erp-ai.mjs`가 인증·고정 경로 호출·요청 공유·캐시를 소유하고 `quota-history.mjs`가
ERP와 데모의 동일한 정상화 규칙을 소유한다. 원본 데이터와 세션은 서버에만 있다.
기존 GPU 이력과 API 청구 비용 소스는 변경하지 않는다. ERP 미연결 환경은 503을
표시하며 다른 서비스의 이력으로 대체하지 않는다. 데모는 별도의 명시적 표본이다.

## 비용과 갱신

선택한 계정 하나만 조회한다. 계정·기간별 30초 캐시(최대 8개), 동일 진행 요청 공유,
동시 ERP 이력 요청 4개, 요청당 10초·응답 2 MiB 제한을 적용한다. 캐시 결과를
사용할 때도 현재 계정 목록을 확인한다. 실패한 재조회에 만료 캐시를 사용하지 않는다.
기존 수집 새로고침은 이력 캐시를 무효화한다. 화면은 계정·기간 변경과 새로고침,
기존 한도 갱신 주기에 맞춰 조회하며 이전 요청의 늦은 결과를 표시하지 않는다.

추가 패키지는 없다. 초기 JS gzip은 동일 감사 도구 기준 104,016 → 105,380바이트
(+1,364바이트), CSS는 10,185바이트 그대로다. 실제 ERP 5계정의 7일 이력을 읽었을
때 계정별 648~676개 표본을 받았다. 계정 목록 조회 후 각 계정 최초 이력 조회는
334~742ms, 즉시 반복은 0.06~0.15ms였고 반복 시 ERP 요청은 0회였다. 단일 실행의
조회 CPU 시간은 7~61ms, 프로세스 최대 RSS는 84,500KiB였다. 이 프로세스에는 자식이
없었다. 이는 로컬 어댑터 측정이며 브라우저 전체 시간·동시 사용자 부하·토큰 비용을
측정한 결과는 아니다.
